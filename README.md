# 医境/MedContex(医院上下文驱动微内核)

医院信息系统（HIS / EMR / LIS / PACS / 集成平台等）之所以长期复杂，并不只是因为功能多、模块多，更因为它天然处在**空间、流程、技术、权限、监管、数据体系和利益相关方**的多重约束之中。本项目把这些复杂性整理成一套可讨论、可建模、可落地的分析框架，用于帮助医院信息化团队、厂商、集成商和研究人员更系统地理解医院系统的真实约束。

本项目不追求给出一个“万能医院系统”，而是希望提供一套**复杂度分类模型、场景案例和架构讨论方法**，帮助团队在规划、改造、集成、数据治理和合规评估时，先看清问题结构，再选择合适方案。

## 为什么需要这个模型

医院不同于一般企业信息系统。它既有封闭办公区域，也有半公开诊疗区域和完全开放的公共区域；既要支持几分钟完成的快速问诊，也要支撑持续数天、数周甚至更长的住院与慢病管理；同时还要兼容硬件设备、软件系统、医保平台、监管接口和公共卫生任务。任何一个局部改动，都可能牵动临床流程、数据安全、外部合规和运维稳定性。

因此，医院系统的复杂性不能只从技术角度理解，也不能只从业务角度理解，而需要同时看到环境、流程、数据、权限、监管和多方期望之间的耦合关系。

## 模型讨论覆盖的九个复杂度维度(初定范围，后续陆续补充)

| 维度 | 核心问题 | 典型场景 |
|---|---|---|
| **空间与公共性** | 医院同时包含封闭、半公开和完全公开区域 | 门诊大厅、诊室、病房、检验科、急诊通道的安全边界不同 |
| **服务周期差异** | 医患关系覆盖短、中、长不同周期 | 急诊几分钟处置、门诊复诊、住院全程管理 |
| **工具来源复杂** | 系统包含纯硬件、软硬件结合和纯软件组件 | 监护仪、影像设备、医保接口、HIS、EMR、集成平台 |
| **权限与密级** | 不同角色对数据的读写、浏览、审计需求不同 | 医生、护士、医保、后勤、外包人员访问边界不同 |
| **利益相关方期望** | 厂商、监管、医保、医务、后勤目标不一致 | 合规记录、临床辅助、费用控制、运营效率之间存在取舍 |
| **技术迭代错配** | 外部技术变化快，内部改造节奏慢 | 新接口、新标准、新设备引入导致局部替换和系统割裂 |
| **病情轻重缓急** | 诊疗流程必须区分紧急程度与规范弹性 | 急诊抢救、普通门诊、慢病随访的容错空间不同 |
| **公共卫生责任** | 医院承担传染病防控、上报和协同任务 | 发热门诊、传染病上报、疾控对接增加数据治理复杂度 |
| **中西医数据差异** | 中医诊疗数据表达与西医存在体系差异 | 辨证、舌脉、方药调整难以完全套用西医结构化模板 |

# 医院事件驱动管理模型（一境模型）

> 以「事件」为最小管理单元的医院管理模型框架。

## 架构简述

本项目探索一种由**事件驱动**，**流程驱动**，**上下文驱动**融合驱动的医院管理模型：以事件为最小管理单元，而非以表单或岗位动作为中心。

### 主线

事件 → 流程 → 处置上下文（意图 / 行为）

### 分层

| 层级 | 核心对象 | 职责 |
|---|---|---|
| 实体层 | 基础元数据，如人员信息，设备信息，空间信息等
| 事件层 | 事件（触发者 / 时间 / 地点 / 人物 / 额外属性） | 捕获发生了什么 |
| 流程层 | 流程、节点 | 决定走哪条路，承载上下文 |
| 处置层 | 处置目标、处置行为、角色与个体 | 决定做什么、做到什么状态 |
| 分析层 | 数据池、分析报告 | 人工 + AI 的二次分析 |
| 决策层 | 决策者、决策流程 | 调整流程结构、响应级别与资源 |

### 关键设计

- **事件多维标注**：空间（公开 / 公共 / 半公共 / 企业内部）、时间（上班下班、工作日节假日、白班夜班）、人物（医务核心 / 患者方 / 后勤外包与驻场）、角色、缓急、密级、权重等。地点与时间属性直接决定流程与处置目标的差异。
- **多重角色**：同一个人同时承载专业身份、员工身份、普通人身份等，事件支持多角色标注，角色影响后续流程与处置(如同时考虑多重角色，只考虑某一角色)。
- **智能匹配**：一个事件可并行触发多个流程、链式触发多个连环事件，减少对人工判断"该走哪个流程"的依赖。
- **角色流程不隐匿**：部分角色，如外部人员（患者、家属、外包）的行为节点嵌入医院内部流程，由内部流程驱动，隐匿了自身的流程化需要。
- **骨干流程不切割**：不同角色的不确定性不同，如外部人员（患者、家属、外包）的行为节点嵌入流程后会影响流程的存续时间和复杂度，常规处理了是把骨干流程切碎为一堆子流程，快进快出，但造成导致上下文丢失，如信息重录等。
- **有限状态机**：每个处置目标都有可枚举、可判定、可归档的状态机。
- **兜底 + 培养池**：事件层「其他事件」、流程层「其他流程」、处置层「其他处置」承接无法归类的情形；兜底实践中的重复模式可被分析，识别，沉淀为新的规范事件，流程与处置。
- **流程间切换**：流程之间存在响应度、密集度、升级/降级关系，可用一个流程完成新旧流程的切换，并行，暂停与承接。
- **决策回归流程**：分析任务对应分析流程，决策任务对应决策流程；决策流程属于"流程的流程"，具有启动—落地—验收的项目管理特征。
- **上下文工程**：人、事物、事件、流程、处置等都作为实体，维护如"流程↔人""事件↔人"等实体之间的多维双向关系；上下文被系统化维护后，AI 可按需调取而无需重新拼接。

### 物理部署架构

模型支持灵活的物理部署策略，适应不同规模与合规要求的医院场景：

- **物理分池设计**：实体层，事件层在物理层面可划分为多个独立的池（Pool），每个池与特定的内部流程域、高频流程或高频事件域强关联（如医疗安全事件池、后勤运维事件池、患者服务事件池）。
- **数据总线与聚合**：各物理分池通过数据总线（Data Bus）或消息队列等技术互联，最终聚合为统一大池（Unified Pool），负责事件跨池广播、流程状态同步、全局查询聚合。
- **多实例部署**：支持部署多个独立实例（每个实例拥有完整的事件层、流程层、处置层），适用于过渡期隔离、安全审计隔离、多院区/多法人实体、灾备与高可用等场景。
- **全局聚合与统一视图**：尽管各实例物理独立，但通过聚合层实现跨实例流程合并唤醒、全局交流协作、统一视图，形成"物理分散、逻辑统一"的架构。

### 上下文实体关系

```
实体 ↔ 事件 ↔ 人(角色/个体) ↔ 流程 ↔ 处置

双向关系：
- 一个流程有多少人参与
- 一个人参与了多少流程
- 一个事件涉及了多少人
- 一个人涉及了多少事件
```

这些多维双向关系被系统化维护后，AI 介入时即可按需调取上下文，无需刻意重新拼接——这是**上下文工程的一种隐形实现方式**。



### 目录结构

```
docs/            设计文档与字段定义
events/          事件模型与类型清单
flows/           流程池与流程映射
dispositions/    处置目标与状态机
context/         实体关系与上下文调取
analysis/        数据池与分析脚本
deploy/          物理部署配置与数据总线
```



## 项目目标

本项目希望回答几类问题：

- 医院系统为什么难改、难集成、难标准化？
- 不同复杂度来自哪些真实约束，而不是单纯的“需求太多”？
- 在规划新系统、改造旧系统或接入外部平台时，如何先识别风险域？
- 如何把临床、运维、安全、监管和数据治理放到同一个框架里讨论？

## 适用人群

- 医院信息化负责人、临床科室信息联络员
- HIS / EMR / LIS / PACS / 集成平台厂商
- 医疗数据治理、医保结算、公共卫生上报相关团队
- 医疗系统架构师、产品经理、实施与运维人员
- 对医院信息化复杂性感兴趣的研究者

## 使用方式

你可以把本模型用于：

- 新建系统前的复杂度评估
- 老系统改造前的影响面分析
- 多系统集成时的边界梳理
- 数据权限与密级分级讨论
- 医保、疾控、监管接口对接前的风险识别
- 中西医并存场景下的数据结构设计讨论
